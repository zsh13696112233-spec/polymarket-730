# 分类公共采集服务

Linux 服务器单进程采集，macOS 客户端只从服务器同步公共数据，并使用本机钱包独立判断和执行。前端仍请求本地 API。服务器不创建钱包、邮件、赎回或交易服务，也没有远程配置和触发扫描接口。上游明确直连，客户端交易仍使用本机代理配置。

## 安装与运行

需要 Python 3.12+ 和 uv，无需安装前端依赖。部署仓库后执行：

```sh
uv sync --locked
cp collection.example.toml collection.toml
sh scripts/start-collection.sh
```

默认监听 `0.0.0.0:8731`；只启动一个 worker。`collection.toml` 设置采集分类、周期、成交下限、窗口和保留时间，重启生效。默认体育、电竞，每 60 秒采集，成交下限 1000 USDC，分析窗口 24 小时，保留 72 小时。重点市场补齐可能包含小于该下限的拆单。周期包含本轮处理时间，超过周期时不重叠启动。

来源持仓按钱包合并市场查询，每轮最多处理 12 个钱包，优先近期买入并为历史队列保留名额；持仓与资料补充限时 25 秒，历史补齐限时 8 秒。已验证持仓缓存 120 秒，出现新成交时重新核验。尚未完成的核验明确标记为 pending，不视为空持仓，也不消耗有效新信号的首次决策机会；超过 180 秒仍未就绪的信号不追买。状态接口 runtime 提供当前阶段、本轮耗时及就绪/待核验来源数。60 秒是目标轮询周期，实际延迟还取决于上游响应和排队量。

如需 systemd，将仓库放到 `/opt/polycopy`，创建专用 `polycopy` 用户并授予该目录和数据目录访问权限，按实际 uv 安装路径调整 `deploy/polycopy-collection.service`，再由管理员安装并启用服务。部署和真实采集须由用户明确授权执行；开发验证仅使用模拟上游。

服务器以 HTTP 提供公共数据，不设置账号或令牌，也不提供传输完整性保证。不要将本地交易 API 的 8730 端口作为公共采集服务暴露。

## 客户端

在系统设置填写服务器 IP、端口，测试连接并保存。在监测设置选择服务器支持的分类；已有客户端保留原分类，服务器不支持的分类暂停。新客户端默认体育、电竞。每 5 秒检查完整增量，界面“立即同步”触发同一同步流程，不会让服务器再扫描一轮。本地没有直接采集回退路径。

首页请求监控记录本地到采集服务器的状态、快照和增量请求，显示分类、开始时间、耗时、HTTP 状态与失败原因。成功的状态检查按服务器合并，累计次数在本地后端重启后归零；快照、增量及失败请求保留在现有容量限制的最近日志中。无新数据是正常成功。这里不接收服务器访问 Polymarket 的请求日志，服务器采集是否新鲜、覆盖是否完整仍看采集状态。

首次连接、重启、断线恢复、游标过期或数据源变化时先追平固定水位，旧信号只建立规则基线，不补买。新增分类先建立基线，其他分类继续消费。新信号与采集完成时间默认最多允许 180 秒；覆盖不完整和来源持仓查询失败均拒绝依赖该数据的自动买入。实时来源持仓、市场、盘口、余额、费用及既有幂等和预占保护仍由本地执行器核验。

取消订阅不会删除个人历史、订单、持仓或账本。已有订单对账继续独立运行；个人持仓对账、赎回和历史结算刷新在本地运行，不依赖采集服务器连接。

## 协议与存储

只读接口为 `/api/collection/v1/status`、`/snapshot`、`/changes`。状态返回数据源 ID、范围版本、最新批次和各分类覆盖。分页需传 `source_id`、`watermark`、`categories`，增量另传 `cursor`；`after` 是批次内变更序号，`limit` 为 1–200。最后一页的 `complete=true` 才允许推进 `scanned_through`。无匹配事件仍推进扫描水位。失效水位返回 409，客户端重建公共基线。

数据库使用 SQLite WAL。服务器有独立 Alembic 迁移链 `backend/collection_migrations`，启动自动升级；本地通过新增迁移保存连接、订阅版本与缓存，保留旧 ID 和交易引用。公共发布和增量日志原子提交；本地完整批次与游标原子提交，规则进度与决策原子提交。金额为十进制字符串，时间带 UTC 标记。分类过滤在服务器分页前执行；同步请求没有执行钱包、个人配置、账本或凭证。

## 备份与恢复

使用 SQLite 的在线备份接口，不能仅复制运行中的 `.db` 而遗漏 WAL。例如在服务器上执行：

```sh
sqlite3 data/collection.db ".backup '/safe-backups/collection.db'"
```

恢复时先停止服务，将备份放回配置的数据库路径，确认所有权后启动。不要覆盖正在打开的数据库。从旧备份恢复应使用新的数据源 ID，避免客户端把回退的游标视为当前数据；可在停机时仅修改公共库：

```sh
sqlite3 data/collection.db "UPDATE collection_meta SET source_id=lower(hex(randomblob(16))) WHERE id=1;"
```

客户端检测数据源变化后只重建公共缓存，个人配置、钱包与交易记录保留。服务器备份不包含客户端数据；每个客户端的个人数据库和钥匙串需分别备份。
